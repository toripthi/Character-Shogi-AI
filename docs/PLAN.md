# 手順テンプレート層（src/plan）

## 呼び出しの順序
`player.chooseMove`：定跡（book）→ **手順テンプレート** → 探索。テンプレートが「次の1手」を返しても、
浅い探索（`safety.depth`、既定2）で最善手より `safety.marginCp`（既定150）を超えて悪ければ採らず、探索に任せる。
有効にする：ペルソナの `plan: "<id>"`（`furi-mamori` は `furi-shiken-mino`）、または `createPlayer({ plan })`。`plan: false` で無効。

## 形式（`src/plan/plans/*.js`、先手視点。後手は盤を180度回して使う）
- `interrupts`：最優先。条件が成り立ち、指せるなら、手順の途中でも先に指す。
- `steps`：上から、最初の「指せる」手を指す。`when` はその条件のときだけ対象（`opponent: "ibisha"|"furi"`、`oppPawnAt: "1d"`）。
- `tail`：steps が尽きた後。
- `stop: true`：その手が済み（または指せない）なら、そこで終わり（tail も指さない）。
- `choose`：重みつきの選択（四間70／三間30）。選ぶのは、その手を指すとき1回だけ。
- 手は USI の盤上の手＋`piece`（駒の種類）。「済み」＝to のマスに自分のその駒がある。「指せる」＝from に自分のその駒があり、手が合法。
  どちらでもなければ飛ばして次へ（止まらない）。

## 速度の外れ値の原因（2026-10-18、ibisha-seme 同士・深さ3・74手）
- 全体196秒のうち、3秒超の19手が147秒（75%）。最長23.7秒。
- 原因1：静止探索が全ノードの約9割（qnodes は nodes の約10倍、緩んだ局面では最大55倍）。深さの上限・delta剪定・取り得の判定がない（`src/search/negamax.js` の quiescenceSearch）。
- 原因2：持ち駒で合法手が100〜200に増える（打てる駒の種類×空きマス）。合法手100以上の手は中央値5.5秒。
- 両方が重なると最長になる。仮想の持ち駒が多い局面（合法手525）は深さ3で4.3秒。上限を保証する仕組みは、既定では入っていない（`search.maxNodes`／`maxDepth` はオプトイン）。

## 速度の外れ値への対策（2026-10-18）
1. **静止探索に上限と剪定**（`src/search/negamax.js`、定数は `constants.js`）：取り合いの連鎖は最大8手（`Q_MAX_DEPTH`）、
   取る駒の価値＋200点でも alpha に届かない取りは読まない（`Q_DELTA_MARGIN`、デルタ剪定）。
   効果：持ち駒なしで9秒かかった局面が0.4秒に。固定値テストは再固定（golden 102局面のうち最善手が変わったのは3件）。
2. **1手あたりのノード数の既定の上限**（`DEFAULT_MAX_NODES` = 20万、nodes+qnodes）：指定がなければ反復深化。
   上限に達したら、完了した最後の深さの結果を返す。`search.budget:false` で従来の固定深さに戻せる。
- 測定（ibisha-seme 同士・深さ3・約115手）：最長 23.7秒 → 7.0秒（1のみ）→ 4.8秒（1＋2）。95パーセンタイル 3.3秒。
  深さ3を完了できなかった手は約7%（深さ2の結果を返す）。持ち駒が多く合法手が130〜190の局面が中心。
- 未対応：持ち駒の打ち駒による枝の多さそのもの（手の並べ替え・打ち駒の絞り込み）、αβ探索の最適化（反復深化・キラー・ヒストリー・Zobrist）。

## ランダム（戦法の振り分け）の実装（2026-11-05、D-029 (e)）
- ランダムは人格ではなく、戦型の選択肢の1つ（対局開始時に居飛車／振り飛車へ振り分ける仕組み）。特性 `random`（group: opening、`choose: {ibisha:50, furibisha:50}`）。`resolvePersona` が、random を居飛車党／振り飛車党に置き換えた2通りの一式（style・bookTags・plan）を `openings.variants` に持つ。通常のペルソナは `openings: null`。
- `createPlayer`：戦法の一式を `variants` に持ち、手番の色ごとの抽選結果（`state.opening`）で、評価・定跡タグ・手順テンプレート・文脈（置換表の作り直し）を切り替える。`player.opening(side)` で抽選結果を引ける。
- 抽選は `newGame(seed)`（作成時は `options.seed`）。先手・後手は別の乱数系統（色ごとにシードを混ぜる）で、手選びの `state.rng` は消費しない。同じシードなら同じ戦法。
- 確認：既存318件は変更なしで通過（通常のキャラの挙動は不変）。新規13件（排他・配分・再現・固定の戦法のキャラとの一致）。
- 手順テンプレート（`plan`）も戦法ごとに切り替わる：variants が戦型ごとの plan を持ち、確定した戦型のテンプレートが効く（居飛車＝`ibisha-basic`、振り飛車＝`furi-shiken-mino`）。ランダムだからといって定跡やテンプレートが消えることはない。

## αβ探索の最適化 ①反復深化の枠（2026-11-05）
順序：①反復深化の枠 → ②置換表と最善手による並べ替え → ③キラー手 → ④プロファイルを見て王手確認など。
- **枠は既にあった**（`think()`：深さ1から順に読み、置換表の Map を使い回す。予算つきは `chooseSearchMoveBudget`）。置換表の最善手による並べ替えも既にある（`orderMovesInt` / `orderAndFilterInt`）。
- **不具合を修正**：`searchBestMove` が候補手ごとに「いま調べた手」を根の置換表に保存していたため、読み終えた根エントリの bestMove が「最後に調べた手」になっていた（10局面すべて）。次の反復の根で最悪手が先頭に並び、反復深化の利点を打ち消していた。全候補を読み終えたとき、本当の最善手を1回だけ保存するようにした（中断した反復は書かない。以前の巻き戻しは不要になったので削除）。
- 効果（10局面・深さ3まで・置換表つき反復深化）：ノード合計 54,841 → 52,144（直接探索 50,028 に対し 1.10倍 → 1.04倍）。**最善手は直接探索と10/10で一致**（以前は5/10が同点の別手）。score は全局面で不変。
- 固定値テスト `identity-tt` を再固定（score は全行で不変。initial の best が 1i1h・3i3h → 9g9f になり、置換表なしの基準線と一致）。回帰テスト `test/search/root-tt.test.js` を追加。
- プロファイル（反復深化＋置換表、10局面×4回）：`_genLegal` 31%、GC 7%、SFEN文字列の生成 約9%（`sfen` 2箇所）、`probeTt`（文字列キーの Map）4%、`orderAndFilterInt` 4.5%、評価 約8%。**置換表の文字列キー（SFEN）まわりで約20%** を使っている。葉ノード（depth 0）でも静止探索の前に全合法手を生成している（詰み判定のため）。

## αβ探索の最適化 ③段階2：Zobristハッシュ（2026-11-05）
打ち切り基準（ユーザー合意）：時間が8%以上減るなら続ける、5%未満なら戻す。
- 事前測定：SFEN文字列の生成は29,564回・1回約0.9µs。計時のオーバーヘッドが大きく、直接計時（上限 約22%）とプロファイル（約5%）の幅が広くて判断できなかったため、**一時コピーに Zobrist を試作して実測**した。試作は 30行（10局面×深さ1〜3）で best・score・nodes・qnodes・ttHits が文字列キー版と完全一致、時間は 121.6ms → 86.1ms（-29.2%）。→ 基準（8%）を大きく超えたので本実装。
  - （手違いの記録）試作の最初の比較は、パッチ用スクリプトがアサーションで止まり未適用のまま「完全一致」と出ていた。適用の確認（`zkey` の使用箇所の数）を入れてやり直した。
- 実装：`FastBoard` に Zobrist（盤×駒の符号、持ち駒の枚数、手番。hi/lo の2つの int32）。`makeMove` で差分更新し、現在値をスタックに積み、`unmakeMove` はスタックから復元する。`zkey()` は 53 ビットの整数（置換表の Map のキー）。区別の単位は SFEN の先頭3フィールドと同じ。置換表のキーは、探索の5か所（`negamax` の probe・store、`ordering` の2か所、`searchBestMove` の根の store）を `fb.zkey()` に替えた。`ShogiBoard.zkey()` も追加。
- 結果（段階1のzipと、10局面・深さ3まで・前後を交互に7回・中央値）：**128.1ms → 91.3ms（-28.8%）**、ノード数 52,144 は不変、30行の best・score・nodes・qnodes・ttHits は完全一致。段階1・2の合計は、別々の測定どおり約 186ms → 約 91ms（約半分）。
- テスト：`test/core/zobrist.test.js`（差分更新と再計算の一致、make→unmake で戻る、約3,000局面で SFEN の先頭3フィールドと1対1・手順前後で同じキー・手番と持ち駒の区別、5,000手超の make でもスタックが伸びて壊れない）。`budget.test.js` の「根エントリが残っていない」は、キーの種類が変わると空振りして常に通ってしまうため、`zkey` で引くように直し、完了した探索では引けることも確認するようにした。`root-tt.test.js` も同様。
- 注意：衝突は検出しない（53 ビット。約 10 万局面で確率 1e-6 のオーダー）。持ち駒の枚数は 0〜19 まで（歩18が最大）。置換表の Map のキーは文字列ではなく数値になった。
- 参考：この10局面では置換表の hit（値の再利用）は合計 2 回しかなく、置換表の効果はほぼ「最善手による並べ替え」。

## αβ探索の最適化 ④段階3：キラー手（2026-11-05）→ 採用せず（打ち切り）
打ち切り基準（ユーザー合意）：ノード数が10%以上減り、かつ時間も5%以上減るなら採用。
- 試作（一時コピー。本体には入れていない）：非捕獲手のβカットで、手数（根からの距離）ごとに2手ずつ記録し、`orderAndFilterInt` で一致する手に加点。反復をまたいで持ち越す版も試した。
- 測定（ノード数は決定的）。10局面（`bench-search` と同じ）：深さ3 で 52,144 → 51,366（-1.5%）、深さ4 で 141,634 → 138,234（-2.4%）。
- 実戦の局面137個（ibisha-seme・furi-mamori・balance・seme の自己対局から5手おきに採取、深さ2・定跡なしで進めたもの）：

  |---|---|---|---|
  | なし | 1,801,355 | 6,309,502 | - |
  | 100 | -1.0% | -5.7% | 0 |
  | 600 / 2000 / 5000 / 9000（置換表手・取る手の次、静かな手の先頭）| -1.2% | -7.0〜7.1% | 0 |
